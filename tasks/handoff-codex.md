## 2. 前提知識（実測で確定。再調査は不要）

対象環境は **Microsoft Store 版 Kindle（WinUI）**。旧 `Kindle for PC`（Qt）とは挙動が違う。
`WindowInfo.GetWindowList()` で見ると、こうなっている。

| hwnd | class | 状態 | 備考 |
|---|---|---|---|
| 393232 | `Microsoft.UI.Windowing.Window` | 表示中 | **これが本体** |
| 2099706 | `Qt5QWindowIcon` | 非表示 | 旧 Kindle for PC の残骸 |
| 11012268 | `Qt5QWindowIcon` | 非表示 | 同上 |

実測でわかっていること:

- **キー入力（pyautogui / SendInput）は普通に届く。** スキャンコード指定は不要
- **F11 は効くが、全画面になるまで実測 1.5 秒かかる。** 押した直後に判定すると必ず失敗扱い
- 最大化時のウィンドウ矩形は `(-11, -11, 1931, 1139)`。画面は 1920x1200 なので
  `is_fullscreen()` は False（判定は正しい）。全画面時は `(0, 0, 1920, 1200)`
- **フォーカスが本文から外れると矢印キーが一切効かなくなる。**
  Escape も Tab も効かない。**本文のクリックだけが復帰手段**（実測で確認）
- **クリックするとツールバーが出る。全画面ではカーソルを Kindle の外へ出せないため自動では消えない。**
  同じ場所をもう一度クリックするとトグルで閉じる
- クリック位置は `(sc_w//2, sc_h//2)` にすること。
  左右端はページ送りになり、`sc_h*0.72` は**全画面時に本を閉じてライブラリへ戻る**
- ダイアログ（`wxdialog`）を閉じてもフォーカスは Kindle に残る。ここは原因ではない

（`'CR' is not recognized` が出ていた）。**.bat は ASCII のみ**にし、日本語表示は Python 側で行う。

## 3. 残課題

### 課題1（追調査で訂正）: 書字方向判定の誤報

**2026-09-20 Codex 追調査:** 以下の当初報告は、別の入力を混同していた。
元ログの「横92.1 / 縦69.7」は、キャプチャが1枚で止まった実行（`1 PNG files found.` / `OCR 1/1 : 001.png`）の結果。
現在の同書籍の `001.png` は横書きの注意書きで、横書き判定が妥当だった（再測定は92.1 / 69.0）。
前任者の `scratchpad/verify_out/run` に残る10枚の縦書き本文は、現行コードのまま54.3 / 86.2で正しく縦判定した。
10枚すべてを実際に OCR し、005/007の本文を画像と目視照合、005/006/007/009のPDF表示も確認した。
判定アルゴリズム・API・キャプチャ処理は変更していない。
詳細・再現手順・残る図表／英字の誤認識は [調査記録](ocr-direction-investigation.md) を参照。

以下は当初の報告を履歴として残す。**この記述だけを根拠に判定処理を変更しないこと。**

- **事象**: 『システム開発と「具体と抽象」』は**縦書き**だが、判定は
  `横書き 92.1 点 / 縦書き 69.7 点 → 横書きの本として OCR します` と出る
- **裏付け**: キャプチャ画像は明らかに縦書き（右から左へ読む）。
  さらにページ送りが**左矢印**で進む＝右綴じ＝縦書きの本、と整合する
- **影響**: 縦書きの本を `jpn`（横書き用）で OCR すると文字化けする（`lessons.md` L-002 参照）。
  34 冊規模で処理しているので、既存 PDF にも誤判定分が混ざっている可能性がある
- **調べ始める場所**: `marge_pngs.py` の書字方向判定（本の中ほど 2 ページを試し読みして
  `jpn` / `jpn_vert` のスコアを比べている部分）
- **ヒント**: ページ送りの向き（`--direction`）は書字方向の強い手がかりになる。
  判定が割れたときに使えないか検討の余地あり

### 課題2: キャプチャ範囲の自動検出（`cmps`）が脆い

- `kindless.py` の `capture()` 内 `cmps()` は、**画面の y=19,20 の 1 行だけ**を走査して
  本の左右端を決めている。オーバーレイ・ライブラリ画面・全画面遷移中など、何かを拾うたびに誤る
- 実測した誤検出:

  | 状況 | 検出結果 | 幅 |
  |---|---|---|
  | 正常（検出失敗→デフォルト） | `1 1` | 1918px ✅ |
  | ライブラリ画面 | `360 2` | 1558px ❌ |
  | クリック後に測定 | `543 2` | 1375px ❌ |
  | 全画面化の直後に測定 | `775 798` | 347px ❌ |

- **つまり「何か検出したとき」は毎回誤っていた**
- 現在は ①操作前・静止後に測る ②検出幅が画面の半分未満なら全幅に戻す、で実害を止めている。
  判定ロジック自体の作り直しは手つかず
- なお `left_margin` / `right_margin`（ini）は「常駐ソフトが画面端にある場合」用。
  この環境にはそういうソフトは無い

## 4. 触るときの注意

1. **UI 自動操作は副作用が本体。** キーやクリックは意図した動作のほかに、
   ツールバー表示・フォーカス移動・レイアウト変更・本を閉じる、を引き起こす
2. **1 行足したら実機で撮った画像を目で見る。** 「枚数が増えた」だけでは不十分。
   中身が切れていないか、ツールバーが写っていないかまで確認する
3. **動いている状態を推測で壊さない。** 「効果が実証できていない」と判断して `moveTo` を
   消した結果、38 枚撮れていたものが 1 枚に落ちた
4. **画面の変化率は「ページが進んだ」の証拠にならない。** 72.82% の変化を「進んだ」と読んだが、
   実際は本が閉じてライブラリへ遷移した変化だった
5. `pag.moveTo()` の行き先を**画面の四隅にしない**。pyautogui のフェイルセーフ座標で、
   次のキー操作が `FailSafeException` で落ちる。10px 内側に置く

## 5. 検証のやり方

### モックテスト（実機不要）

```
python tests/test_capture_loop.py
```

`tests/test_capture_loop.py` に 16 項目ある。**Kindle が起動していなくても動く**
（`kindless.pag` / `ImageGrab` / `SetForeWindow` / `IsWindowAlive` を偽物に差し替えるだけ）。
終了コードは 0（全通過）か 1（失敗あり）。pytest は使っていないので依存の追加も不要。

`capture()` に手を入れたら、まずこれを通すこと。ここで落ちるなら実機を触る必要はない。
見ている内容は各項目のラベルに日本語で書いてある。

偽画面（`FakeScreen`）は「進む向きのキー」以外では変化しないので、
向きが逆のときのフォールバックもここで検証できる。

### 実機テスト（ダイアログを通さず自動化できる）
`main()` はタイトル入力ダイアログを出すので自動化しづらいが、**`capture()` を直接呼べば不要**。

```python
cfg = read_config(KindleSSConfig(), ini)
cfg.nextpage_key = 'left'
hwnd = GetVisibleWindowHandleWithName('Kindle', 'kindle.exe')
kindless.SetForeWindow(hwnd)
if not kindless.is_fullscreen(hwnd):
    pag.press(cfg.fullscreen_key)
    kindless.wait_until_fullscreen(hwnd, cfg.fullscreen_wait)
saved = kindless.capture(cfg, out_dir, 1, hwnd)
```

これを別プロセスで起動し、出力 PNG が一定枚数に達したら `terminate()` すれば短時間で終わる。
`ini` は `base_save_folder` だけ作業用フォルダに差し替えたコピーを使い、`c:\kindle_ss` を汚さないこと。

**確認は必ず画像を開いて目で見る**（枚数と画像サイズだけで判断しない）。
判定を機械化するなら、上端・下端 40 行の平均輝度が 255 に近いか（ツールバーが写っていないか）が使える。

### 注意
- 実行中は PC を操作しない。マウス・キーボードが Kindle に干渉する
- 検証で Kindle のフォーカスやページ位置が壊れることがある。
  おかしくなったら Kindle を閉じて開き直すのが確実
- テスト用に本を開いた状態にしておくこと（ライブラリ画面のままだとライブラリを撮り続ける）
